# 统一前端项目的 Node 版本、包管理器、第三方依赖包

## 一、锁定项目 Node 版本：`engines` + `engine-strict`

### 1.1 基础配置

`package.json` 中通过 `engines` 声明允许的 Node / npm 版本：

```json
"engines": {
  "node": "14.x || 16.x",
  "npm": ">=6.14.18"
}
```

官方字段说明（推荐使用官方英文文档）：

权威地址：https://docs.npmjs.com/cli/v10/configuring-npm/package-json#engines


### 1.2 各包管理器的默认行为对比

| 包管理器 | 默认行为 | 是否默认阻断 |
|---|---|---|
| npm（v6/v7/v8/v9/v10） | 版本不匹配时输出黄色 **warning** | ❌ 不阻断，继续安装 |
| Yarn Classic（yarn v1） | 版本不匹配直接**报错退出** | ✅ 阻断 |
| pnpm | 版本不匹配输出 **warning** | ❌ 不阻断 |


### 1.3 `engine-strict` 的正确用法与边界

`.npmrc` 中加入 `engine-strict`，可以让 npm 在版本不匹配时**由警告升级为报错退出**：

```ini
engine-strict=true
```

⚠️ **重要边界条件：**

1. `engine-strict` **仅对 npm CLI 生效**，对 yarn、pnpm **无效**。
2. 该字段的作用范围是 **npm install 流程**，不会限制 `node` 命令本身的执行。
3. 在 CI 或封装脚本中使用 `npx`、`npm ci` 的某些场景下，校验不一定按预期触发。
4. npm 官方并未将 `engine-strict` 作为强校验的长期推荐方案（npm v9 起默认策略仍是不阻断）。

### 1.4 更稳妥的现代方案（推荐组合）

单纯依赖 `engines` + `engine-strict` 可控性较弱，更可靠的做法：

1. 在项目根目录添加 **`.nvmrc`**（内容为 `14` 或 `16`），配合 `nvm` / `fnm` / `volta` 自动切换。
2. 增加 **`preinstall` 脚本**硬校验 Node 版本（见下文方案），不匹配直接抛错退出。
3. 需要跨包管理器统一时，`engines` 只作为「提示声明」，真正的强制由脚本层完成。

## 二、锁定包管理器：`only-allow` + `preinstall`

### 2.1 安装与配置

```bash
npm install only-allow -D
```

`package.json`：

```json
"scripts": {
  "preinstall": "only-allow npm"
}
```

允许取值：`only-allow npm` / `only-allow pnpm` / `only-allow yarn`。

### 2.2 关键坑点

1. **`--ignore-scripts` 可直接绕过**：执行 `npm install --ignore-scripts` 会跳过全部生命周期脚本，`preinstall` 不执行，锁管理器方案直接失效。CI 环境出于安全管控常加 `--ignore-scripts`，此时锁形同虚设。
2. **pnpm 不执行 npm 的 `preinstall` 脚本**：用户直接跑 `pnpm install` 时，pnpm 不会触发 `package.json` 中的 `preinstall`，`only-allow npm` 根本无法拦截 pnpm。
   > 结论：**`only-allow` 对 pnpm 的拦截能力天生有短板**，这是最常见的坑。
3. `preinstall` 是 **npm 的生命周期钩子**，不是跨包管理器的统一钩子，作用范围有限。

### 2.3 补充说明

- 现代项目若要求更强约束，可配合 husky / simple-git-hooks 在 git 层再加一道校验。
- 也可用自写 `preinstall` 脚本硬校验（不依赖第三方包），例如读取 `process.env.npm_execpath` 判断实际使用的包管理器并拦截。

## 三、强制指定依赖版本：resolutions / overrides

### 3.1 三种写法的正确边界

| 包管理器 | 字段 | 适用版本 |
|---|---|---|
| **Yarn Classic（yarn v1）** | `resolutions` | yarn 1.x 专属 |
| **Yarn Berry（yarn 2/3/4）** | `overrides` | ⚠️ 已弃用 `resolutions`，改为 `overrides` |
| **npm** | `overrides` | ⚠️ **npm v8.3+ 才支持**，v6/v7 无效 |
| **pnpm** | `pnpm.overrides` | pnpm 支持 |

### 3.2 写法示例

**Yarn Classic：**

```json
"resolutions": {
  "vue": "2.6.14",
  "vue-server-renderer": "2.6.14",
  "vue-template-compiler": "2.6.14"
}
```

**npm（需 >= 8.3）：**

```json
"overrides": {
  "vue": "2.6.14"
}
```

**pnpm：**

```json
"pnpm": {
  "overrides": {
    "vue": "2.6.14"
  }
}
```

### 3.3 风险提示

1. **`resolutions` / `overrides` 属于暴力覆盖依赖版本**，会**绕过语义化版本（semver）约束**，强行把所有包固定在指定版本。
2. 存在**隐蔽的兼容性与安全风险**：被覆盖版本的依赖可能存在已知漏洞或与其上游包不兼容，安装时不会提示。
3. 建议**仅在应急、且充分验证兼容性后使用**，避免作为常规依赖管理手段。
4. 注意 pnpm 的 `peerDependencyRules` 与 `overrides` 用途不同（前者用于处理 peer 依赖冲突告警），勿混淆。

## 四、三套机制定位速查

| 机制 | 定位 | 作用层面 | 典型生效对象 |
|---|---|---|---|
| `engines` + `engine-strict` | 版本**提示 / 约束** | 原生能力 | npm（engine-strict 仅 npm） |
| `only-allow` + `preinstall` | **拦截包管理器** | 脚本层 | 主要对 npm / yarn（pnpm 有绕过） |
| `resolutions` / `overrides` | **强制覆盖依赖版本** | 依赖解析层 | 各包管理器对应字段 |

> ⚠️ 关键提醒：**没有任何一套配置能同时锁死 npm + yarn + pnpm 三者的全部行为**。各包管理器机制割裂，`engine-strict` 只作用于 npm，`preinstall` 对 pnpm 失效，`resolutions` / `overrides` 字段又随版本不同。

## 五、推荐落地组合

针对不同诉求给出推荐配置：

### 场景 A：仅统一 npm 工作流

```jsonc
// package.json
{
  "engines": { "node": ">=16 <18", "npm": ">=8.3" },
  "scripts": {
    "preinstall": "only-allow npm"
  }
}
```

```ini
# .npmrc
engine-strict=true
```

### 场景 B：多包管理器团队，希望尽量约束

1. 根目录放 `.nvmrc`（配合 volta / nvm 自动切换 Node）。
2. 用自写 `preinstall` 脚本硬校验 Node 版本与包管理器，抛错退出（不依赖 only-allow 对 pnpm 的短板）。
3. `engines` 仅作提示声明，不依赖 `engine-strict` 做强校验。

> 建议实际落地前，在 CI 与本地各跑一次 `npm install`、`pnpm install`、`yarn` 验证拦截与校验是否符合预期。
